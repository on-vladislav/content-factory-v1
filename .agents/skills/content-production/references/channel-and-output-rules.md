# Каналы и форматы результата

## Общие правила

На текущем этапе готовить публичные материалы только для Telegram, MAX и сайта. Другие площадки подключать только по прямому решению Влада.

Каждый материал должен иметь одну аудиторию, проблему, главную мысль, цель, бизнес-результат и CTA. Не начинать с фраз «Сегодня расскажу», «Сегодня покажу» или «Сегодня разберём». Технологии упоминать только после бизнес-задачи, потерь и результата.

Влад должен быть показан не только как консультант и архитектор решения, но и как специалист-практик, который может сам собрать бота, автоматизацию, сайт, интеграцию, внутренний инструмент или прототип. Практическую реализацию показывать после бизнес-контекста, чтобы материал отвечал и на запрос аудитории: «я видел, что ты сделал, мне такое сделаешь?»

## Telegram

- Использовать личную подачу и достаточную глубину рассуждения.
- Показывать логику консультанта, практический вывод и мягкий CTA.
- Делать короткие абзацы для мобильного экрана.
- Комфортная длина для публикации с обложкой — `900–1000` видимых символов с учётом хештегов.
- Технический предел подписи к обложке через Telegram Bot API — `1024` видимых символа. Основной Telegram-текст не должен превышать этот предел, если публикация должна выйти одним сообщением «обложка + подпись».
- Для основного экспертного поста добавлять в конце 1–2 утверждённых хештега отдельной строкой.

## MAX

- Сохранять одну главную мысль и простой заголовок.
- Делать текст короче Telegram-версии, сохраняя причинно-следственную логику.
- Комфортная длина — `500–800` символов, редакционный максимум — `1000` с учётом хештегов.
- Использовать минимум сложного форматирования.
- Сохранять те же хештеги, что и в Telegram-версии.

## Сайт

- Показывать результат и ценность с первого экрана.
- Структурировать доказательства, оставляя технические детали вторичными.
- Вести CTA к диалогу, самопроверке или вопросу аудитории. CTA к продукту «Анализ бизнес-процессов» использовать только тогда, когда Влад отдельно подтвердил, что такой следующий шаг уместен для конкретного материала.
- Не переносить социальный пост без структурной переработки.
- Создавать статью или кейс только как долгосрочный актив: для подтверждённого кейса, устойчивого клиентского или поискового вопроса либо глубокой продуктовой темы.
- Если материал будет лишь повторять социальный пост, сообщать, что статья на сайт не нужна.

## Утверждённые хештеги

`#разбор_процессов`, `#кейсы`, `#управляемость_бизнеса`, `#автоматизация_бизнеса`, `#потери_в_бизнесе`.

Личные и ситуативные публикации могут выходить без хештегов.

Для каждой публикации отдельно озвучивать решение по хештегам. Если они нужны — добавлять 1–2 одинаковых хештега в Telegram и MAX. Если не нужны — не добавлять и кратко объяснять причину.

## Обложка

- Для каждой основной публикации озвучивать решение: нужна обложка или нет.
- Если обложка нужна, объяснять её функцию и создавать сразу; если не нужна — не создавать файл.
- Использовать квадрат `1254 × 1254 px` и стилевой референс из `AGENTS.md`.
- Использовать плашки: `Разбор проблемы` и `Разбор процесса` → `РАЗБОР ПРОЦЕССОВ`; `Разбор продукта` → `РАЗБОР ПРОДУКТА`; `Ошибка руководителя` → `ОШИБКА РУКОВОДИТЕЛЯ`; `Кейс` → `КЕЙС`.
- Для `Личного бренда` плашку не использовать.
- Заголовки обложки, Telegram и MAX по умолчанию делать одинаковыми.

## Сторис

- Для каждой основной публикации озвучивать решение: нужна сторис или нет.
- По умолчанию использовать один экран; серию делать только для кейса, запуска или сложной последовательности.
- Если сторис нужна, готовить точный текст, визуал или инструкцию, ссылку и CTA.
- Для отдельного изображения использовать `1080 × 1920 px`.
- В центральном потоке сохранять `reports/YYYY-MM-DD-topic-name-story.md` и при необходимости `reports/YYYY-MM-DD-topic-name-story.png`.
- Не создавать сторис, если она лишь повторяет пост и не даёт дополнительной пользы.

## График

Основные экспертные публикации для Telegram и MAX планировать два раза в неделю: по понедельникам и четвергам в 12:00, часовой пояс `Europe/Moscow`, если утверждённый график не задаёт иное. Личные публикации не превращать в обязательный дополнительный график.

При изменении даты синхронно обновлять метаданные, имя файла, путь к обложке и `content-registry.yaml`. Не менять утверждённый материал без подтверждения.

## Метаданные публикации

Использовать существующую схему проекта. Для нового черновика:

```yaml
---
content_id: agency-telegram-problem-03
channel: telegram
content_type: problem-analysis
status: draft
planned_date: 2026-08-12
scheduled_at:
timezone: Europe/Moscow
cover_path:
cta_type: self-audit
product: business-process-analysis
needs_manual_review: true
source:
  - path/to/source.md
---
```

Не заполнять `scheduled_at`, пока Влад не разрешил публикацию и не подтвердил время. Формировать `content_id` по схеме `[project]-[channel]-[type]-[number]`; после публикации не менять.

`approved` означает, что текст и комплект утверждены Владом, но не разрешает внешнюю публикацию или планирование. `scheduled` устанавливать только после отдельного прямого решения Влада с указанием площадки, даты и времени.

## Контент-план

Для каждой позиции фиксировать дату, канал, аудиторию, проблему, главную мысль, источник, формат, CTA и статус `draft`. Название темы без источника и главной мысли не считать готовой позицией плана.

Для планов из собственного опыта использовать `reports/2026-08-30-source-events-registry.md` без тем про разработку логотипа и личную базу данных, если Влад отдельно не решил иначе.

Не включать в план внутренние диалоги по презентации, самопрезентации, позиционированию и альтернативным вариантам сайта, если тема не превратилась во внешний продукт, проект, кейс или решение задачи. Собственный сайт можно показывать как факт собранного рабочего актива, но без раскрытия внутренней кухни.

Замороженные и незавершённые проекты не описывать как готовую услугу; по ним допустимы осторожные разборы ограничений, критериев готовности, проверяемых гипотез и вопросов к аудитории. Слабые места работающего кейса можно показывать, если это не раскрывает клиентские секреты и помогает читателю понять реальное ограничение процесса.

Календарные поводы использовать как ситуативный угол подачи, а не как самостоятельный источник темы. Формальные поздравления не добавлять в основной экспертный график.
