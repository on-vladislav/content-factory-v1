# Локальная проверка Content Factory v1

Дата проверки: 2026-10-02  
Контур: локальный Windows + Docker, без VPS и без внешней публикации

## Проверенная конфигурация

- PostgreSQL 16 в отдельном Docker volume;
- API Content Factory на `127.0.0.1:8765`;
- PostgreSQL доступен только на `127.0.0.1:55432`;
- Windows Worker с исходящим polling;
- JSON Schema заданий и результатов для постов и контент-планов;
- публикация заменена безопасной локальной симуляцией.

## Пройденные сценарии

### Реальная генерация поста

1. Worker передал разрешённое тестовое задание и реестр исходных событий в Codex CLI.
2. Диагностические попытки подтвердили обработку timeout, невалидного служебного счётчика и превышения лимита Telegram без потери Job.
3. После нормализации производного счётчика и явного ограничения длины новый Job `JOB_550107FFC9F8` завершился с первой попытки.
4. Post Package `local-content-factory-real-03` сохранён в `REVIEW`, `manual_lock = false`, публикация `NOT_AUTHORIZED`.
5. Фактическая длина Telegram-текста пересчитана Worker и составила 967 видимых символов.

### Согласование поста

1. Локальный тестовый пост прошёл `REVIEW → REVISION_REQUESTED → REVIEW` с новой AI-ревизией.
2. Ручная правка создала третью ревизию и включила `MANUAL_LOCK = true`.
3. Повторная AI-корректировка после ручной правки была отклонена.

### Контент-план

1. Создан отдельный `GENERATE_CONTENT_PLAN`.
2. Реальный Job `JOB_64719F48C56D` завершился с первой попытки и создал четыре темы в `REVIEW`.
3. В безопасном локальном сценарии план прошёл `REVIEW → REVISION_REQUESTED → REVIEW`.
4. Ручная правка создала третью ревизию и включила `MANUAL_LOCK = true`.
5. Повторная AI-корректировка была отклонена, тестовый план отдельно переведён в `APPROVED`.
6. Утверждение плана не создало Post Package, расписание или публикацию.

### Базовый цикл публикации в симуляции

1. Создан `GENERATE_POST` со статусом `PENDING`.
2. Worker атомарно получил Job и lease.
3. Первая попытка реального Codex не получила сетевой доступ из песочницы текущей сессии.
4. По тайм-ауту Job корректно перешёл в `WAITING_RETRY` и сохранил ошибку `CODEX_TIMEOUT`.
5. Вторая попытка в режиме `--simulate` создала Post Package.
6. Job получил `COMPLETED`, Post Package — `REVIEW`.
7. Ручная правка создала ревизию №2 и включила `MANUAL_LOCK = true`.
8. Отдельное действие перевело пост из `REVIEW` в `APPROVED`.
9. Симуляция Publisher до планирования ничего не опубликовала.
10. Отдельное действие перевело пост в `SCHEDULED`.
11. Симуляция Publisher обработала только `SCHEDULED` и сохранила локальную ссылку.

## Фактический результат

```text
PENDING
  → CLAIMED
  → PROCESSING
  → WAITING_RETRY
  → CLAIMED
  → PROCESSING
  → COMPLETED

Post Package:
REVIEW
  → ручная правка + MANUAL_LOCK
  → APPROVED
  → SCHEDULED
  → PUBLISHED (simulation)
```

## Что подтверждено

- выключение или недоступность Codex не приводит к потере Job;
- повторная попытка использует то же задание;
- `APPROVED` не запускает публикацию;
- планирование выполняется отдельным действием;
- Publisher выбирает только `SCHEDULED`;
- ручная правка хранится как отдельная ревизия;
- пост и контент-план поддерживают одинаковые действия корректировки и ручной блокировки;
- реальная генерация поста и контент-плана работает через `codex exec` без OpenAI API;
- Worker безопасно читает только явно указанные файлы внутри корня проекта;
- `AGENTS.md` и дополнительные источники теперь вкладываются в задание самим Worker;
- локальные сервисы не доступны через внешний сетевой интерфейс;
- существующие Docker-проекты не изменялись.

Проверка кода: 12 unit-тестов, синтаксическая проверка Python и загрузка всех JSON Schema. Размер локальной PostgreSQL-базы после тестов — около 8 МБ.

## Что ещё не проверено

- локальный n8n и Telegram Preview;
- обмен с Notion;
- реальный Telegram Bot API;
- перенос на VPS, HTTPS и резервное копирование production-базы.

Передача конкретного тестового задания, `AGENTS.md` и реестра исходных событий в OpenAI была отдельно разрешена Владом и выполнена. Для Notion и Telegram нужны отдельные приёмочные действия, потому что они изменяют внешние сервисы.
